## Why
Moe: "use tengrids for the data returned from the research". The research loop's outputs stay exactly
as they are (`research/RESEARCH.json`, gate unchanged). What changes is how that data is *shown*: a
canvas data grid from his fork **tengrids** replaces the hand-built competitor table on the customer
results tab and is added to the dashboard's company-research run page.

## Deliverables (several commits are fine; every subject starts with `P11:`)
1. **Dependencies** (`package.json` + lockfile): `react@19`, `react-dom@19`, peers `lodash@4`, `marked@16`,
   `react-responsive-carousel@3`, and `"@glideapps/glide-data-grid": "file:dashboard/vendor/tengrids/packages/core"`.
   Vite config: add `@vitejs/plugin-react` (devDependency) so `.jsx` compiles; keep both existing inputs.
2. **Build step**: `make vendor-tengrids` → `git submodule update --init dashboard/vendor/tengrids` then
   `npm ci` + `npm run build -w packages/core` inside it, **skipped when `packages/core/dist/esm/index.js` is
   newer than the submodule's HEAD commit** (so `make verify` stays fast). `make verify` and the dashboard
   `vite build` depend on it. Document in `README.md` (Verify section) and `system/config/environment.md`.
3. **Grid model (pure, tested)** `dashboard/web/src/research-grid/model.js`:
   `researchToGridModel(research, comparison?)` → `{ tabs: [{ id, label, columns:[{title,width,kind}], rows:[[cell…]] }] }`
   with three tabs: **competitors** (name, website (uri), what they do well, products found (count)),
   **prices** (your product, your price, competitor, their product, their price, delta % (yours vs theirs),
   source (uri), verified ✓/– from `comparison` state when given), **ideas** (#, idea, rationale).
   Numbers are numbers (`GridCellKind.Number`), links are `GridCellKind.Uri`, everything else `Text`,
   all `allowOverlay:false` (read-only grid). Missing prices render "—" and sort last.
4. **React island** `dashboard/web/src/research-grid/ResearchGrid.jsx` + `mount.js` exporting
   `mountResearchGrid(el, { research, comparison, variant })` → returns `{ update(next), unmount() }`.
   Uses `DataEditor` from tengrids with a theme derived from `dashboard/design/tokens.json` (Geist font,
   row height 41 px, `border.subtle` #e4e4e7, `text.*` colors — same numbers the rest of the UI uses) and a
   tab strip (plain buttons, same `.pill` style as the customer page) to switch between the three tabs.
   Column widths fit the content; the grid height = min(rows, 12) × 41 + header. Include the mandatory
   `<div id="portal">` once per page (customer.html, index.html). Import `@glideapps/glide-data-grid/dist/index.css`.
5. **Customer results tab** (`dashboard/web/src/customer/app.js`): replace the `comp-table` block under
   "Your competitors" with a `<div data-card="research-grid">` that mounts the island (research + comparison
   if the API provides it; keep About / What we learned / How your site will win cards as they are — the
   design mocks are authoritative for everything except the table itself, per Moe's request).
   Unmount on tab change / re-render; no duplicate roots on SSE patches.
6. **Dashboard run page** (`dashboard/web/src/app.js`): on a company-research run, fetch
   `/api/engagements/:id/research` (once per run id; cache in the store) and mount the island in a card
   `research grid` above the existing comparison card; keep the comparison card (it is the verified view the
   operators use). The patch path (`fillComparisonCard` area) must update the island via `update()`, not remount.
7. **Tests** (node:test + jsdom, run by `make verify`):
   - `model.test.mjs`: the three tabs from the myjam-shaped fixture (6 competitors, 14 products, 4 ideas);
     delta % math; nulls → "—" sorted last; uri cells for every source; verified flag from `comparison`.
   - `mount.test.mjs`: stub `HTMLCanvasElement.prototype.getContext` (return a minimal 2D context object with
     the methods DataEditor calls — see `dashboard/vendor/tengrids/packages/core/vitest.setup.ts` for what
     upstream stubs) and `ResizeObserver`; assert `mountResearchGrid` renders one root, `update()` keeps it,
     `unmount()` removes it; assert the customer results render mounts exactly one grid and that a re-render
     with the same research does not create a second `#portal`.
   - existing suites stay green: `node --test "dashboard/server/*.test.mjs" "dashboard/web/*.test.mjs"`.
8. **React dedupe (verified, required)**: the submodule's own `npm ci` installs its React (19.1.1) under
   `dashboard/vendor/tengrids/node_modules`, and the linked package resolves `react` from there while the app
   uses the root React → two Reacts → `TypeError: Cannot read properties of null (reading 'useMemo')` and an
   empty grid. Vite config **must** set `resolve: { dedupe: ["react", "react-dom"] }`. The orchestrator
   proved this on a spike: without dedupe → 0 canvases + that error; with dedupe → 5 canvases, grid drawn.
9. **Headless render check (mechanical proof, part of `make verify`)**: script `dashboard/tools/grid_render_check.mjs`
   that builds a fixture page (customer results with the myjam-shaped research fixture, mounted via the real
   `mountResearchGrid`), serves `dist/` on a free localhost port, runs
   `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu --virtual-time-budget=10000 --dump-dom <url>`
   and asserts: no `window.onerror` text captured in a `<pre id="err">`, `document.querySelectorAll("canvas").length >= 1`,
   and `#portal` present exactly once. Exit non-zero otherwise. (Lighthouse's Chrome is already a verified
   dependency of the website gate, so this adds no new tool.)
