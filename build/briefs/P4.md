## How the research loop produces files (amendment to P2.3)

Inside Pi the executor has **one** tool: `scrape`. It cannot write files. So:
- The executor's **final assistant message** must end with one fenced ```json block of shape `{"RESEARCH": <RESEARCH.json object>, "SOURCES_MD": "<markdown string>"}`.
- Add a per-loop **materialize hook** to `loop_runner.mjs`: after the executor turn, call `loop.materialize({ outputPath, workdir, db, loopRunId })`. For `company-research` (`system/loops/company-research/materialize.mjs`) it parses the *last* fenced JSON block from the executor output, writes `research/RESEARCH.json` (pretty-printed) and `research/SOURCES.md` into the customer repo, and returns `{ ok: true, files }`. Materialization is **deterministic orchestrator code** (no model call); it records the executor's Pi trace ref in the files it writes (`SOURCES.md` frontmatter `trace`), and `SOURCES.md` follows the §8 markdown rules — frontmatter `updated`/`trace`, body rewritten, `## History` preserved and appended (one line per materialization) — never overwritten wholesale. On any parse/shape failure it returns `{ ok: false, error }` and the runner records the iteration **without calling the reviewer**: `reviewer_verdict = "revise"`, `reviewer_notes = "FORMAT: " + error`, event `iteration.recorded` with `materialize: false`. Add a test for this path to `test_loop_runner.mjs` (fixture executor output with no JSON block → iteration 1 `revise` with `FORMAT:` notes, reviewer fixture never called).
- The `website` executor writes through guarded Pi file tools (Phase 5) and has **no** materialize hook; `loop.materialize` is optional in the runner (skip when absent).

## P4.1 — Executor + reviewer prompts

`system/loops/company-research/executor.md` (Grok via Pi, tool `scrape` only). Template variables: `{{idea}}`, `{{site_url}}`, `{{customer_name}}`, `{{adjusted_instructions}}`, `{{previous_reviewer_notes}}`. Instructions must make the model:
1. If `site_url` is set: scrape the homepage, then the product/service/pricing pages it links to; build `company.customer_products` from what it actually read (each with `id` like `cp_01`, `name`, `price` number or null, `url`). If no URL: derive `customer_products` from the idea as the planned offerings (`price: null`, `url: ""`). **At least one customer product is required.**
2. Find ≥ 5 competitors (same market / geography as implied by the idea or site). For each competitor: scrape its site (and pricing page if any) — **only URLs that were scraped may appear anywhere in the JSON**; `url` fields must be the exact scraped URLs.
3. `product_matches`: for as many customer products as possible (target ≥ 25 % of `customer_products`, by distinct `customer_product_id`), a competitor product with a numeric `competitor_price` and the `source_url` that was scraped and showed that price.
4. ≥ 3 `enhancement_ideas`, each with a non-empty `rationale` grounded in a competitor observation.
5. `SOURCES_MD`: a table of **every** scrape attempted in this run — `| url | http_status | note |` — including refusals (`refused: robots`) and non-200s. The gate cross-checks this against the `scrapes` table, so it must be complete.
6. End with the single fenced JSON block described above; no prose after it. Respect `{{adjusted_instructions}}` and `{{previous_reviewer_notes}}` when present.

`system/loops/company-research/reviewer.md` (Luna via Pi, no tools). Inputs rendered by the runner: the materialized `RESEARCH.json`, `SOURCES.md`, and a table of `scrapes` rows for this loop run (`url`, `http_status`). The prompt lists the five gate checks verbatim from SOP §6 and requires the reviewer to:
- assess each check by number (`1.`–`5.`), quoting the offending item when failing;
- end with exactly one fenced JSON block `{"verdict": "revise" | "approve" | "reject" | "escalate", "notes": "<check-numbered critique>"}`; `approve` only if it believes all five will pass; `reject` for fabricated URLs (a URL not in the scrapes table); `escalate` only for policy problems (e.g. scraping refused everywhere, market cannot be identified).

`system/loops/company-research/index.mjs` exports `{ name, executorPrompt(vars), reviewerPrompt(vars), materialize, gate: "system/gates/research_gate.py" }` and renders the templates.

## P4.2 — `system/gates/research_gate.py`

CLI: `research_gate.py --workdir <customer-repo> --db <path> --loop-run-id <id>`; prints a JSON array `[{"check_name", "passed", "detail"}]` (always all five, in order) and exits 0 iff all passed, else 1. Check names (used verbatim in the dashboard):

| # | `check_name` | Rule |
|---|---|---|
| 1 | `schema_valid` | `research/RESEARCH.json` exists and validates against `system/gates/research_schema.json` (JSON Schema for SOP §6, `additionalProperties` allowed; required keys and types enforced; `customer_products` minItems 1). Add `jsonschema` to the venv (`uv pip install --python system/tools/.venv/bin/python jsonschema`) and record the version. |
| 2 | `competitors≥5` | ≥ 5 competitors, and for each, `url` has a `scrapes` row for this `loop_run_id` with `http_status = 200`. Detail lists the failing competitors. |
| 3 | `product_coverage≥25%` | distinct `customer_product_id` in `product_matches` ÷ `len(customer_products)` ≥ 0.25, and **every** match has a numeric `competitor_price` and a `source_url` with a 200 `scrapes` row. Detail shows `matched/total` and offending matches. |
| 4 | `enhancement_ideas≥3` | ≥ 3 ideas with non-empty `idea` and `rationale`. |
| 5 | `sources_complete` | **multiset** comparison: every `scrapes` row for this run (any status, including NULL/refused, **including duplicate URLs**) has its own row in `research/SOURCES.md` with matching `url` and `http_status` (`refused` for NULL). Detail lists missing `(url, status)` pairs and their counts. |

If `RESEARCH.json` is missing or unparsable, check 1 fails with the reason and checks 2–5 fail with `detail = "skipped: schema_valid failed"`.

Fixtures: `system/gates/fixtures/research/<case>/` with `research/RESEARCH.json`, `research/SOURCES.md`, and `scrapes.json` (rows to seed: `url`, `http_status`). Cases: `pass`, `fail_schema`, `fail_competitors` (only 4 with 200), `fail_coverage` (matches lack a 200 source), `fail_ideas` (2 ideas), `fail_sources` (a seeded scrape missing from SOURCES.md).

Tests: `system/tools/.venv/bin/python -m unittest system/gates/test_research_gate.py` — for each case: temp DB via `migrate.sh`, seed `scrapes`, run the gate, assert exit code and that exactly the expected `check_name` is `passed: false` (for `pass`: all true, exit 0). Wire into `make verify`. Hook the gate into the runner's `gateRunner` for `company-research` (spawn the venv python, parse JSON).

**Verify:** paste the unittest output (`Ran 6 tests … OK`) and `make verify; echo exit=$?`.
