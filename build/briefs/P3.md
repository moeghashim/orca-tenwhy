## Architecture you are implementing

- The orchestrator is **deterministic Node code** (`system/orchestrator/`) that is the **sole writer** of `engagements` / `loop_runs` / `iterations` / `gate_checks` / `events`. It calls the orchestrator *model* (Claude Fable 5) only for two judgement tasks: composing **adjusted instructions** after a failed loop run (P3.3) and **rewriting knowledge-base synthesis** (P3.4). Both go through a model adapter (`system/orchestrator/adapters/claude.mjs`, real; `adapters/fixture.mjs`, tests).
- `loopctl` never runs loops inline. It writes rows; a single **daemon** (`loopctl daemon`, or `tick()` called directly in tests) processes pending work. This keeps one writer.
- IDs are prefixed for the dashboard: `eng_<8 hex>`, `run_<8 hex>`, `it_<8 hex>`, `chk_<8 hex>`, `apr_<8 hex>`.
- Customer repos live under `state/customers/<slug>/` (add `state/customers/`, `state/pi-sessions/`, `state/scrapes/`, `state/scrape/` to `.gitignore`).

## P3.2 — Scheduler / daemon

`system/orchestrator/orchestrator.mjs` exports `tick({ db, config, adapters, runLoop, deploy })` — one pass over pending work, safe to call repeatedly:
1. `engagements.status = new` → set `running`, event `engagement.started`, queue loops with no unmet edges (from `loops.yaml`: `company-research`). Queue = insert `loop_runs` (status `queued`, attempt 0).
2. For each `queued` run: build inputs (`company-research`: idea, site_url; `website`: **handoff payload** = `{ researchJsonPath, sourcesPath, companyName, productCount, competitorCount }` computed from the research run's outputs) and call `runLoop(...)` from P2.3. Record event `handoff` with the payload when a downstream loop is queued. Loops with independent inputs may run concurrently (`Promise.all`); in v1 the graph is linear, but the code must derive order from `edges`, not hardcode it.
3. `gate_passed` on `company-research` → P3.4 absorption, then queue `website`.
4. `gate_passed` on `website` → engagement `awaiting_approval` (P3.6). **No deploy here.**
5. `gate_failed` → P3.3. `needs_human` (loop) → engagement `needs_human`, event `engagement.needs_human`.
6. Unprocessed `approvals` rows (no `events.kind = approval.processed` with that approval id) → P3.6.

`loopctl daemon` calls `tick` every interval; a `SIGINT` stops it cleanly.

**Verify:** `node --test system/orchestrator/test_scheduler.mjs` with fixture adapters and a fixture `runLoop`: research runs first; the website run is queued only after research `gate_passed`; the `handoff` event payload is recorded and matches the research outputs; a fabricated second root loop in a test config runs concurrently with research (assert both started before either finished).

## P3.3 — Failure policy

On `gate_failed`:
- `attempt < caps.retry_cap` (2) → call the orchestrator model: prompt contains the loop's failed `gate_checks` (name + detail) and the last iteration's `reviewer_notes`; ask for concise adjusted instructions. **Mechanical guarantee:** whatever the model returns, the stored `adjusted_instructions` must contain every failed `check_name` and the verbatim last reviewer notes — append a `Failed checks:` / `Reviewer notes:` block if the model omitted them. Insert a new `loop_runs` row with `attempt + 1`, `adjusted_instructions`, event `loop_run.retry`.
- `attempt == 2` and failed → engagement `needs_human`, event `engagement.needs_human` with payload `{loop, lastRunId, failedChecks}`.
- Customer change requests (P3.6) **do not** count: they start at `attempt 0` with `change_request_id` set.

**Verify:** `node --test system/orchestrator/test_failure_policy.mjs` — forced failure every time → runs with attempts 0, 1, 2; attempts 1 and 2 have distinct, non-empty `adjusted_instructions` that contain the failed check names and reviewer notes; then engagement `needs_human` with the event.

## P3.4 — Knowledge-base absorption

`system/orchestrator/knowledge.mjs` → `absorbResearch({ repoDir, researchJson, traceRef, model, now })`:
- Targets: `company/OVERVIEW.md`, `company/POSITIONING.md`, `company/FINDINGS.md`, `company/competitors/<slug>.md` (one per competitor), `company/products/<slug>.md` (one per customer product). Missing files are created from a minimal template.
- For each file: model rewrites the **synthesis body** from `RESEARCH.json` (fixture returns deterministic text); code sets frontmatter `updated = now`, `trace = traceRef`, and **appends** one `## History` line. History is never rewritten; existing lines are preserved byte-for-byte.
- Commit in the customer repo: `research: absorb <loop-run-id>`; push to `origin`.

**Verify:** `node --test system/orchestrator/test_knowledge.mjs` — after one absorb: frontmatter valid, History has 1 new line; after a second absorb with a different trace: synthesis replaced, History has 2 lines in order, first line unchanged; `lintFrontmatter` returns `[]`.

**Verify:** test drives two research passes → every touched `company/*.md` has two dated History entries.

## P3.6 — Approval state machine

In `tick`:
- website `gate_passed` → engagement `awaiting_approval`, event `engagement.awaiting_approval`.
- `approvals.action = approve` (engagement must be `awaiting_approval`, else event `approval.rejected_state` and skip) → call `deploy({ engagementId, repoDir })` (injected; real implementation arrives in P5 — until then `system/orchestrator/deploy.mjs` exports a function that **throws `not implemented until P5.1/P5.2`**, and tests inject a fixture that records calls) → on success engagement `complete`, event `engagement.complete` with `{ liveUrl }`; on throw → `needs_human`.
- `approvals.action = request_changes` → new `website` loop run: `attempt 0`, `change_request_id = <approval id>`, `adjusted_instructions = "Customer change request:\n" + notes`, engagement back to `running`, event `engagement.change_requested`.
- Mark each processed approval with event `approval.processed` `{approvalId, action}`.
- `loopctl approve <id>` / `loopctl request-changes <id> --notes` insert `approvals` rows (fallback for the customer UI); they validate `awaiting_approval` and exit 1 otherwise.

**Verify:** `node --test system/orchestrator/test_approval.mjs` drives: running → awaiting_approval (deploy fixture call count = 0) → approve → deploy called once → complete; separately awaiting_approval → request_changes → new website run with `change_request_id`, notes in `adjusted_instructions`, `attempt = 0`, and the orchestrator retry counter of the previous chain untouched; approve while `running` → event `approval.rejected_state`, no deploy.

Wire every `node --test` file into `make verify` (a single `node --test system/orchestrator/` invocation is fine).
