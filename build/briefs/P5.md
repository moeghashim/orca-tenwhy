## How the website loop works

The loop has a **design step** and a **build step** inside one loop run:

1. **`prepare` hook (new, optional per loop)** — runs once before iteration 1. For `website` it runs the *reviewer model* (Luna) as the designer: `system/loops/website/design.md` prompt + the handoff payload (`RESEARCH.json`, company name, products) → final fenced JSON `{"tokens": <brand/tokens.json object>, "BRAND_MD": "...", "logo_svg": "<svg …>", "IMAGE_BRIEF_MD": "..."}`; `system/loops/website/materialize_design.mjs` writes `brand/tokens.json`, `brand/BRAND.md`, `brand/logo.svg`, `brand/IMAGE_BRIEF.md` into the customer repo. Event `loop_run.prepared` with the trace ref. Failure → loop run `gate_failed` with a `gate_checks` row `check_name = "design_spec"`, `passed = 0` (so the orchestrator retries with adjusted instructions).
2. **Executor iterations** — Grok via Pi builds the Vite site under `website/` using **Pi's built-in file tools only**: `--tools read,write,edit,ls,grep,find` (no `bash`: SOP §0.3 — the model never gets a shell; `npm run build` is run by the gate, and build errors come back through the reviewer/gate as `revise` notes). Guard extension `system/loops/website/pi-guard.ts`: `pi.on("tool_call", …)` blocks any `write`/`edit` whose resolved path is outside the customer repo's `website/` and `brand/` directories (return `{ block: true, reason }`). Add a unit test that the guard blocks `../../etc` and allows `website/src/main.js`. Update `loops.yaml` `website.tools` to `[read, write, edit, ls, grep, find]` and `company-research.tools` stays `[scrape]`; keep `lint_loops.js` passing.
3. **Reviewer iterations** — Luna via Pi (no tools) reviews a **manifest** the runner renders: file tree of `website/` + contents of `index.html`, `src/*` (truncate each file to 8 kB), `brand/*.md|json`, `RESEARCH.json` product names, and the last gate output if any. Critiques against the six gate checks by number; ends with the `{verdict, notes}` JSON block.

Prompts: `system/loops/website/design.md` (Luna designer: derive palette/type/spacing tokens **from the customer's brand, not tenwhy's**; SVG logo ≤ 4 kB, wordmark-based, valid XML; `BRAND.md` voice + do/don't; `IMAGE_BRIEF.md` = a table `| asset | path | description | size |` of images Moe will generate manually — paths under `website/public/images/…`), `system/loops/website/executor.md` (Grok: Vite vanilla static site, `website/package.json` with `vite` only, `index.html` + `src/main.js` + `src/style.css` using `brand/tokens.json` values, pages: home + one page per product group + contact, all internal links relative and valid, every IMAGE_BRIEF asset wired as an `<img src="<declared path>">` with a generated SVG placeholder file at that path, copy grounded in RESEARCH.json — company name and product names verbatim, no invented claims), `system/loops/website/reviewer.md`. `system/loops/website/index.mjs` exports `{ name, prepare, executorPrompt, reviewerPrompt, gate }`.

## P5.4 — `system/gates/website_gate.py`

CLI as `research_gate.py`; prints all six checks in order; exit 0 iff all pass.

| # | `check_name` | Rule |
|---|---|---|
| 1 | `brand_assets_valid` | `brand/tokens.json` validates against `brand_tokens_schema.json`; `brand/logo.svg` parses (`xml.etree`) with `svg` root. |
| 2 | `build_ok` | in `website/`: `npm ci` (or `npm install` when no lockfile) then `npm run build` exit 0 within 5 min; capture the last 40 lines of stderr into `detail` on failure. |
| 3 | `links_ok` | parse every `dist/**/*.html`; every internal `href`/`src` (relative or root-relative, ignoring `http(s):`, `mailto:`, `tel:`, `#`) resolves to a file in `dist/` (try `path`, `path/index.html`, `path.html`). 0 broken. |
| 4 | `placeholders_wired` | every row of `brand/IMAGE_BRIEF.md` (table parse) has its `path` present in `dist/` **and** referenced by some `<img src>`/`srcset`/CSS `url()` in `dist/`. |
| 5 | `copy_grounded` | visible text of `dist/**/*.html` (tags stripped) contains `company.name` and ≥ 3 distinct `customer_products[].name` from `research/RESEARCH.json` (case-insensitive, whitespace-normalised). |
| 6 | `lighthouse≥85` | start `npx vite preview --port <free port> --strictPort` in `website/`, wait for the port, run `lighthouse http://127.0.0.1:<port>/ --only-categories=performance,accessibility --output=json --output-path=<tmp> --chrome-flags="--headless=new" --quiet`, stop the preview; both category scores × 100 ≥ 85. `detail` = the two scores. |

Fixtures `system/gates/fixtures/website/<case>/` (each a tiny customer repo with `brand/`, `website/` prebuilt sources, `research/RESEARCH.json`): `pass`, `fail_brand` (malformed SVG), `fail_build` (syntax error in `main.js`), `fail_links` (dangling href), `fail_placeholders` (brief row without an `<img>`), `fail_copy` (product names missing), `fail_lighthouse` (a page with a 3 s synchronous busy-loop script before first paint and a 4 MB inline base64 image, plus missing alt text / no `<html lang>` to sink accessibility). Tests: `system/tools/.venv/bin/python -m unittest system/gates/test_website_gate.py` — `pass` → all six true; each `fail_*` → exactly that check false (`fail_build` may also fail 3–6 with `detail = "skipped: build_ok failed"` — implement that skip). Lighthouse runs make this test slow (~1–2 min); keep it in `make verify` but also expose `make verify-fast` that skips gate check 6 via `WEBSITE_GATE_SKIP_LIGHTHOUSE=1` (the fixture test for check 6 must still run in `make verify`). Hook into the runner's `gateRunner` for `website`.

**Verify:** unittest output (`Ran 7 tests … OK`) and `make verify; echo exit=$?`.
