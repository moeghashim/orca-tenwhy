## Server additions — `dashboard/server/` (write endpoints on a **separate, writable** connection; all other endpoints stay read-only)

- `POST /api/engagements` `{ idea?, site_url?, customer_name? }` → 400 unless at least one of idea/site_url; **delegates the create to the orchestrator process** by spawning `bin/loopctl new "<idea>" [--url …] [--name …]` (inheriting `TENWHY_DB`, `TENWHY_REPO_BACKEND`) and returning its printed id as `{ id }` (201). The dashboard server never opens a general loop-state writer: UI creation is a **trigger**, while approve/request-changes remain its only direct DB writes (SOP §0.2/§10). Timeouts/non-zero exit → 502 with the CLI's stderr summary.
- `GET /api/engagements/:id` → the engagement + its loop runs, iterations, gate checks (subset of the snapshot filtered by engagement).
- `GET /api/engagements/:id/research` → `{ research: <RESEARCH.json>, comparison: {columns, rows} }` from the customer repo (404 until the research gate passed).
- `GET /preview/:id/*` → static files from the engagement's persisted repo dir `website/dist/` (404 until the website gate passed), served with `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: sandbox allow-scripts` so the results page can iframe it while the preview runs in an opaque origin. `GET /api/engagements/:id/preview-manifest` → read-only `{ pages: [{ path, title }] }` listing `dist/**/*.html` (drives the page checklist).
- The results page embeds the preview as `<iframe sandbox="allow-scripts" src="/preview/<id>/">` — no `allow-same-origin`, so preview content cannot call the write APIs.
- `POST /api/engagements/:id/approve` → inside one `BEGIN IMMEDIATE` transaction: **409** unless `engagements.status = awaiting_approval` **and** no unprocessed `approvals` row exists for the engagement (no `approval.processed` event for it) — this rejects double-clicks and concurrent submissions; else insert the `approvals` row (`approve`) and return `{ ok: true }`. The endpoint inserts **only** the approval row; the orchestrator emits every lifecycle event when it processes it.
- `POST /api/engagements/:id/request-changes` `{ notes }` → 400 if `notes` empty; same transactional 409 rule; insert `approvals` (`request_changes`, notes); `{ ok: true }`. Write endpoints additionally require the header `X-Tenwhy-Client: customer-ui` and reject any request whose `Origin` is not the server's own origin (CORS is not enabled), so the sandboxed preview iframe cannot call them.
- SSE: `GET /api/events?engagement=<id>&since=…` filters patches to that engagement (reuse the P6 stream).

## Pages — `dashboard/web/src/customer/`

1. **Start** (`#/` on the customer entry): `Meet tenwhy` + one-line promise; mascot (black circle, two white rounded-bar eyes; float 4 s + blink 5 s keyframes); white rounded-24 input card with the two inputs, helper line, black `↑` circle submit; mono footer `research → review → build → launch · ~20 minutes · nothing published without your ok`. Submit → `POST /api/engagements` → navigate to loading.
2. **Loading** (`#/e/<id>`): mascot with spinning ring; cycling phase title/sub; 5-step checklist driven by **real events** over SSE (not timers):
   | step | done when |
   |---|---|
   | 1 reading your site / brief | first `loop_run.started` for `company-research` |
   | 2 researching the market | first `iteration.recorded` for `company-research` |
   | 3 planning | `gate.checked` for `company-research` with all passed (or `handoff`) |
   | 4 building your site | first `iteration.recorded` for `website` |
   | 5 final checks | `gate.checked` for `website` **with an all-pass payload**; a failed gate leaves step 5 active ("in progress") while the orchestrator retries |
   Done = filled black `✓` circle; active = spinning border-top circle + "in progress"; upcoming at 45 % opacity; progress bar with sweep shimmer + `step n of 5`; copy `you can keep this page open — nothing is published without your ok`. `engagement.status = awaiting_approval` → auto-advance to results. `needs_human` → a calm "we've paused to check something — we'll pick this up" state (no button). Reload-safe: initial state comes from `GET /api/engagements/:id`, then SSE.
3. **Results** (`#/e/<id>/results`): pill segmented control with two tabs:
   - **Research**: plain-language cards from `/research`: *about your business* (`company.summary`), *what we learned* (✓ bullets from competitor summaries), *how your site will win* (numbered, from `enhancement_ideas`), competitor table with the design's four columns — `practice · pricing shown · what they do well · online booking` in the mock, whose copy is sample content for a dental customer; keep the same four-column layout with labels `competitor · pricing shown · what they do well · website`, where the competitor name is the external link (`↗`) and the last column shows the competitor's site host; never invent a feature column the research does not contain + the comparison table (`{columns, rows}`, ✓/⚑ cells, shared renderer with the ops dashboard).
   - **Website design**: the drafted homepage in a neutral browser frame = `<iframe src="/preview/<id>/">` (site uses the customer's brand colours from `brand/tokens.json`, never tenwhy's); sidebar cards: page checklist (from `/preview-manifest`) + "built from your research — nothing invented".
   - Both tabs share the actions: **Approve & launch** → `POST …/approve` → "launching…" state → on `engagement.complete` event show the `live_url` (from the event payload) as a link; **Request changes** → textarea + submit → `POST …/request-changes` → back to loading at step 4 with copy "rebuilding with your notes". Disable both while the request is in flight; show a 409 as "this project isn't waiting for approval right now".
   These are the **only** write actions in the front end besides creating the engagement.
