1. **Daemon wiring** (`system/orchestrator/cli.mjs:154`, `orchestrator.mjs runDaemon`): `loopctl daemon` currently calls `runDaemon({ intervalMs })` with no `tickOpts`, so `tick` has no `runLoop`/`adapters`/`gateRunner`/`absorbResearch` and would crash on the first queued run. Add `system/orchestrator/wiring.mjs` → `buildTickOpts({ repoRoot, dbPath })` returning `{ config, runLoop, adapters: { loop: createPiAdapter(...), orchestrator: createClaudeAdapter(), gateRunner }, absorbResearch, deploy }` where `gateRunner` spawns `system/tools/.venv/bin/python <loops.yaml gate> --workdir … --db … --loop-run-id …` and parses its JSON array, and `absorbResearch` binds the Claude adapter as `model`. `runDaemon` and `loopctl daemon` use it. Test: `buildTickOpts` resolves every dependency to a function and `gateRunner` on a fixture gate script returns parsed checks.
2. **Inputs reach the prompts** (`loop_runner.mjs:146`): `runLoop` drops the `inputs` argument the scheduler passes (idea/site_url for research, handoff payload for website). Accept `inputs`, store them on the run (`events` payload of `loop_run.started` and pass to the loop's prompt renderer / `buildExecutorPrompt` as `{{idea}}`, `{{site_url}}`, `{{handoff}}`). Test: fixture adapter captures the executor prompt and asserts the idea/site_url and handoff JSON appear.
3. **Distinct adjusted instructions per attempt** (`adapters/claude.mjs:37`, `failure.mjs`): the model prompt ignores `attempt`; two retries with the same failures can produce identical text. Mechanically prefix `Attempt <n>/<retry_cap> — previous adjusted instructions did not resolve: <check names>` and include the previous run's `adjusted_instructions` (so each attempt differs even if the model repeats itself); pass `attempt` and `previousInstructions` to the model prompt. Test: forced-failure test asserts `adjusted_instructions` of attempts 1 and 2 are non-equal **when the model fixture returns the same text both times**.
4. **Claim the approval before deploying** (`orchestrator.mjs:221`): insert `approval.processed` (or an explicit `approval.claimed`) **before** calling `deploy`, then `engagement.complete`/`needs_human` after; a crash mid-deploy must not lead to a second deploy on the next tick. Test: deploy fixture that throws after recording a call → second `tick` does not call deploy again; engagement is `needs_human` with `deploy_failed`.
5. **Deterministic repo dir** (`orchestrator.mjs:29`): `customerRepoDir` prefix-matches `slugify(customer_name)`, so a suffixed engagement (`<slug>-<id>`) resolves to the first customer's repo. Persist the slug: read it from the `engagement.created` event payload (`json_extract(payload, '$.slug')`) and only fall back to the slug heuristic when absent. Test: two engagements with the same customer name resolve to two different dirs.
